Почему мы создаем Deployment, а не сразу Pod?
Deployment это контроллер верхнего уровня, который управляет жизненным циклом Pod-ов и предоставляет критически важные возможности, недоступные при создании голого Pod-а
Причины создания Deployment:
1.1 Самовосстановление: если Pod упадет или будет удален, Deployment автоматически создаст новый для поддержания заданного количества реплик
1.2 Декларативное обновление: Deployment управляет Rolling Update, позволяя обновить версию приложения без даунтайма
1.3 Откат: в случае неудачного обновления Deployment позволяет одной командой откатиться к предыдущей стабильной версии
1.4 Масштабирование: количество реплик меняется простым изменением числа replicas в манифесте

В чем разница между Liveness и Readiness пробами? Что произойдет, если провалится каждая из них?
Liveness Probe (проба живости):
2.1 Проверяет, не завис ли контейнер (жив ли процесс)
2.2 При провале: kubelet убивает контейнер и перезапускает его
Readiness Probe (проба готовности):
2.3 Проверяет, готов ли контейнер принимать трафик (прогрелся ли кэш, подключилась ли база данных)
2.4 При провале: контейнер не убивается, но удаляется из списка endpoints соответствующего Service и не получает трафик до восстановления готовности

Что такое "requests" и "limits" для CPU и памяти? Почему важно их указывать?
Requests это гарантированный минимум ресурсов, который будет выделен контейнеру при его запуске
Scheduler использует requests для выбора ноды, на которой достаточно свободных мощностей
Limits это жесткий потолок, который контейнер не может превысить
По CPU при превышении троттлится (замедляется), по памяти при превышении контейнер убивается (OOMKilled)
Важность указания:
3.1 Без requests scheduler может разместить Pod-ы неоптимально, что приведет к нестабильности при росте нагрузки на ноду
3.2 Без limits один утекший контейнер может занять всю память ноды и убить соседние процессы (noisy neighbor problem)

Как Service находит свои Pod-ы?
Service находит Pod-ы с помощью механизма Labels и Selectors
Схема работы:
4.1 При создании Pod-а в метаданных прописываются произвольные метки (labels), например app: backend, version: v1
4.2 В манифесте Service указывается секция selector с точно такими же парами ключ-значение
4.3 Service автоматически сканирует все Pod-ы в namespace и строит список Endpoints, куда включает IP-адреса только тех Pod-ов, чьи labels совпадают с селектором
4.4 При падении Pod-а или изменении его меток список endpoints обновляется динамически

Какой тип сервиса (ClusterIP, NodePort, LoadBalancer) используется для внутреннего общения, а какой — для внешнего доступа?
ClusterIP это тип по умолчанию, используется только для внутреннего общения между компонентами внутри кластера
Дает виртуальный IP, доступный только изнутри Kubernetes
NodePort открывает порт на каждой ноде кластера (диапазон 30000-32767) и пробрасывает трафик в Service
Используется для внешнего доступа в тестовых окружениях или когда нет облачного балансировщика
LoadBalancer автоматически создает внешний облачный балансировщик (AWS ELB, GCP LB), который получает публичный IP и направляет трафик на ноды
Это стандартный способ внешнего доступа для продакшен-нагрузок в облаке

Что такое "Rolling Update" в контексте Деплоймента?
Rolling Update это стратегия обновления приложения без даунтайма, при которой новые Pod-ы постепенно заменяют старые
Процесс:
6.1 Создается один или несколько новых Pod-ов с обновленной версией образа
6.2 Kubernetes ждет, пока новые Pod-ы станут Ready (пройдут Readiness Probe)
6.3 После этого старые Pod-ы по одному удаляются (terminated)
6.4 Параметры maxSurge (сколько новых Pod-ов можно создать сверх лимита) и maxUnavailable (сколько старых Pod-ов может быть недоступно) управляют скоростью и безопасностью процесса
6.5 В случае ошибки в новой версии можно выполнить откат до предыдущей ревизии
