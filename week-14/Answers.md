В чем разница между Continuous Integration, Continuous Delivery и Continuous Deployment?
Continuous Integration (CI) это практика частого слияния изменений кода в основную ветку с обязательным автоматическим запуском сборки и тестов для каждой интеграции
Цель — быстрое обнаружение конфликтов и ошибок
Continuous Delivery (CDelivery) расширяет CI: после успешных тестов код автоматически готовится к выкатке в продакшен, но само развертывание выполняется вручную (по нажатию кнопки)
Continuous Deployment (CDeployment) это полная автоматизация, при которой каждое изменение, прошедшее все тесты, автоматически выкатывается в продакшен без участия человека

Почему тесты должны запускаться до сборки Docker образа (или хотя бы до его пуша?
Тесты должны запускаться до пуша Docker образа по следующим причинам:
2.1 Экономия времени и трафика: нет смысла тратить минуты на сборку тяжелого образа и его загрузку в регистри, если код заведомо нерабочий
2.2 Безопасность регистри: в регистри не попадают битые артефакты с уязвимостями или ошибками, а образы всегда пригодны для деплоя
2.3 Ранняя обратная связь: разработчик быстрее узнает о провале на стадии легковесных тестов, чем на стадии загрузки образа
Оптимальный пайплайн: линтеры и юнит-тесты -> сборка артефакта (jar, бинарник) -> интеграционные тесты -> только потом docker build и docker push

Зачем нужно кэширование зависимостей в CI пайплайне?
Кэширование зависимостей нужно для ускорения пайплайна и снижения сетевой нагрузки
При каждом запуске без кэша CI-раннер заново скачивает все библиотеки из интернета (npm install, pip install, maven download), что может занимать минуты
Причины использовать кэш:
3.1 Скорость: загрузка кэшированных зависимостей с локального стораджа в разы быстрее скачивания извне
3.2 Стабильность: исключается риск сбоя внешнего репозитория пакетов во время билда
3.3 Экономия ресурсов: снижается нагрузка на публичные пакетные регистри

Что такое "Secret" в контексте CI/CD? Как безопасно передать пароль от Docker Hub в пайплайн?
Secret это конфиденциальная информация (пароль, токен, SSH-ключ), используемая пайплайном для доступа к внешним системам
Безопасная передача пароля от Docker Hub в пайплайн:
4.1 Секрет ни в коем случае не хранится в открытом виде в коде репозитория или в файлах docker-compose
4.2 Секрет заносится в защищенное хранилище CI/CD системы (GitLab CI/CD Variables, GitHub Secrets, Jenkins Credentials) в замаскированном виде
4.3 В пайплайне значение подставляется через переменную окружения, которая маскируется в логах
4.4 Для Docker Hub: секрет передается в переменной, затем используется команда docker login -u

Что такое "Matrix Build" (матричная сборка)?
Matrix Build это стратегия параллельного запуска одного и того же пайплайна с разными комбинациями переменных для тестирования в гетерогенных средах
Пример: нужно протестировать библиотеку на Node.js версий 18, 20 и 22 в операционных системах Linux и Windows
Вместо написания отдельных джобов создается одна матрица, которая автоматически перемножает переменные и генерирует 6 параллельных джобов
Это гарантирует работоспособность кода во всех поддерживаемых окружениях без дублирования конфигурации

Почему нельзя хранить конфиги продуктовой среды в репозитории кода (или можно, но осторожно)?
Нельзя в открытом виде, потому что:
6.1 Безопасность: продуктовые конфиги содержат секреты (пароли БД, токены API), которые при коммите становятся доступны всем, у кого есть доступ к репозиторию, и навсегда остаются в истории git
6.2 Разделение доступа: разработчики должны иметь право читать код, но не всегда должны видеть продуктовые учетные данные
Можно, но осторожно, при соблюдении правил:
6.3 Хранить только несекретные параметры (таймауты, размеры пулов) в открытых конфигах
6.4 Секретные значения выносить во внешнее хранилище (Sealed Secrets, Vault, CI/CD Variables) и подставлять на этапе деплоя
6.5 Использовать подход GitOps с шифрованием (Mozilla SOPS, Sealed Secrets), чтобы зашифрованный конфиг мог храниться в репозитории, но расшифровываться только на стороне кластера
