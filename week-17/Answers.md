Какие критерии вы использовали при разделении монолита на микросервисы (или при проектировании сервисов)?
Основные критерии разделения:
1.1 Bounded Context (ограниченный контекст) из Domain-Driven Design: сервис владеет своей предметной областью и терминологией без пересечения с другими
1.2 Разные причины для изменений (Single Responsibility): сервис меняется только по одной бизнес-причине, независимо от других
1.3 Независимое масштабирование: компоненты с разной нагрузкой (например, поиск и авторизация) выносятся отдельно, чтобы масштабировать их индивидуально
1.4 Разные нефункциональные требования: части системы с высокими требованиями к latency или доступности выделяются в изолированные юниты
1.5 Данные и транзакции: границы сервиса проходят там, где можно разорвать ACID-транзакции и перейти к eventual consistency без нарушения бизнес-логики

Почему вы выбрали именно этот стек технологий (язык, БД, протоколы)?
Критерии выбора стека:
2.1 Язык: выбран с учетом экспертизы команды, экосистемы (библиотеки, фреймворки) и требований к производительности (например, Go для высоконагруженных сетевых сервисов, Python для data-интенсивных задач)
2.2 База данных: реляционная выбрана там, где нужны ACID-гарантии и сложные связи, документная — для гибкой схемы и высокой скорости записи, key-value — для кэширования
2.3 Протоколы: REST для публичного API и простоты отладки, gRPC для внутреннего межсервисного взаимодействия с высокой нагрузкой и строгими контрактами
2.4 Инфраструктура: Kubernetes для оркестрации, так как обеспечивает самовосстановление, декларативное управление и cloud-портабельность

Как ваши сервисы справляются с ошибками (retry, circuit breaker, graceful degradation)?
Стратегии обработки ошибок:
3.1 Retry с экспоненциальной отсрочкой и jitter: при временных сбоях (network blip, таймаут) запрос повторяется до 3 раз с увеличивающейся задержкой и случайным разбросом для избежания эффекта громового стада
3.2 Circuit Breaker: при превышении порога ошибок за интервал времени цепь размыкается и последующие запросы сразу возвращают fallback-ответ, не нагружая падающий сервис, с периодической проверкой на восстановление
3.3 Graceful Degradation: если зависимый сервис недоступен, система продолжает работу в урезанном режиме (например, рекомендации заменяются на дефолтный список популярных товаров вместо падения всей страницы)
3.4 Таймауты на всех исходящих вызовах: каждый вызов имеет разумный deadline, чтобы зависший запрос не блокировал поток и не истощал пул соединений

Как организован деплой и обновление вашей системы без простоя (Zero Downtime)?
Zero Downtime Deployment обеспечивается через:
4.1 Rolling Update в Kubernetes: новые Pod-ы заводятся постепенно, после успешного прохождения Readiness Probe старые Pod-ы удаляются, трафик не прерывается
4.2 Graceful Shutdown: при сигнале SIGTERM сервис перестает принимать новые запросы, завершает текущие в течение grace period (например, 30 секунд) и только потом останавливается
4.3 Миграции БД без блокировок: используются только аддитивные миграции (добавление колонок), никогда не выполняются деструктивные изменения (удаление, переименование) в одном деплое с кодом
4.4 Совместимость API: новая версия сервиса поддерживает старый формат запросов как минимум один релиз (стратегия Tolerant Reader)

Что было самым сложным в интеграции всех компонентов вместе?
Наиболее сложные аспекты интеграции:
5.1 Распределенные транзакции и консистентность данных: обеспечить согласованность бизнес-процессов без распределенных транзакций, внедряя паттерны Saga и Outbox для надежной публикации событий
5.2 Отладка и трейсинг: отследить сквозной путь запроса через десяток сервисов без единой точки входа, потребовалось внедрение распределенной трассировки (Jaeger) и единого формата correlation-id во всех сервисах
5.3 Контракты API и ломка обратной совместимости: при параллельной разработке несколькими командами синхронизация изменений в контрактах требовала строгого процесса review .proto файлов и использования инструментов проверки обратной совместимости (buf breaking changes)

Что бы вы улучшили, если бы у вас был еще месяц?
План улучшений:
6.1 Покрытие интеграционными и контрактными тестами: увеличить количество тестов, проверяющих взаимодействие сервисов по реальным контрактам, добавить Pact-тесты для верификации consumer-driven contracts
6.2 Мониторинг и алертинг на основе SLO (Service Level Objectives): перейти от мониторинга инфраструктурных метрик (CPU, память) к мониторингу бизнес-метрик (латентность конкретных эндпоинтов, процент ошибок) и настроить алерты на бюджеты ошибок
6.3 Хаос-тестирование: внедрить регулярный Chaos Engineering для проверки устойчивости системы к отказам (убийство Pod-ов, сетевые задержки, отключение зависимостей)
6.4 Документация Runbook: создать операционные руководства для дежурных инженеров с четкими алгоритмами действий при каждом типе алерта
