1. Критерии разделения на микросервисы
Система разделена на три сервиса по следующим критериям:
Разная нагрузка: REST API (tickets-api) обслуживает внешних клиентов и требует масштабирования под веб-трафик. gRPC сервис (tickets-grpc) работает внутри системы с высокой интенсивностью. Их можно масштабировать независимо.
Разные протоколы: Внешние клиенты (браузеры, мобильные приложения) говорят на REST/HTTP. Внутренние сервисы общаются быстрее через gRPC/HTTP2 с бинарным Protobuf.
Ответственность: Nginx отвечает только за маршрутизацию и балансировку. tickets-api — за валидацию и REST-контракт. tickets-grpc — за бизнес-логику и хранение.
Независимое развёртывание: Каждый сервис в своём Docker-контейнере. Можно обновить gRPC сервис, не трогая REST API.

2. Почему выбран этот стек технологий
Python + FastAPI — быстрая разработка, встроенная валидация через Pydantic, автоматическая документация Swagger. Идеально для REST API.
gRPC + Protobuf — бинарный протокол, работает поверх HTTP/2. Даёт сильную типизацию контрактов между сервисами и высокую скорость по сравнению с REST. Выбран для внутреннего общения, где важна производительность.
Nginx — лёгкий, проверенный временем обратный прокси. Умеет маршрутизировать, балансировать нагрузку и проверять здоровье бэкендов.
Docker + Docker Compose — изоляция сервисов, воспроизводимость окружения, запуск одной командой.
In-memory хранилище — для простоты отладки в учебном проекте. В продакшене можно заменить на PostgreSQL или Redis без изменения бизнес-логики.

3. Как сервисы справляются с ошибками
Retry (повторные попытки):
Nginx автоматически повторяет запрос к следующему здоровому экземпляру при ошибке
restart: unless-stopped перезапускает упавший контейнер
Circuit Breaker (предохранитель):
Healthcheck с failureThreshold: 3 — после трёх провалов контейнер считается нездоровым и выводится из балансировки
Graceful Degradation (плавная деградация):
Если tickets-grpc недоступен, tickets-api возвращает понятную ошибку, а не падает сам
Nginx возвращает 502 с информативным сообщением при недоступности бэкенда
Health Checks:
Все сервисы имеют эндпоинт /health
Docker проверяет здоровье каждые 10 секунд
Nginx не шлёт трафик на нездоровые экземпляры
Валидация входных данных:
Pydantic (REST) и Protobuf (gRPC) отсекают некорректные данные на входе
Некорректный JSON возвращает 422 с описанием ошибки

4. Zero Downtime Deployment
Система использует стратегию Rolling Update:
start-first: новый контейнер запускается и проходит health check до остановки старого
failure_action: rollback: если health check нового контейнера провален — автоматический откат на старый
parallelism: 1: единовременно обновляется один контейнер
Nginx продолжает слать трафик только на здоровые экземпляры
Процесс: docker-compose build → docker-compose up -d — и система обновляется без перерыва в обслуживании.

5. Что было самым сложным в интеграции
Сетевое взаимодействие: Настройка Docker-сети, чтобы контейнеры видели друг друга по именам (tickets-api, tickets-grpc), а не по IP-адресам
Порядок запуска: depends_on с condition: service_healthy гарантирует, что API не стартует раньше gRPC сервиса, а Nginx — раньше API
Разные протоколы: REST (JSON) и gRPC (Protobuf) требуют разной обработки и сериализации, но это же даёт гибкость
Health check для gRPC: В отличие от HTTP, для gRPC нужна проверка через открытие сокета

6. Что можно улучшить при наличии месяца
База данных: Заменить in-memory хранилище на PostgreSQL с миграциями (Alembic)
Мониторинг: Добавить Prometheus + Grafana для сбора метрик (RPS, latency, ошибки)
Трейсинг: Внедрить Jaeger или Zipkin для отслеживания запросов между сервисами
Kubernetes: Перейти с Docker Compose на Kubernetes (Helm-чарт уже готов с недели 13)
Service Mesh: Добавить Istio/Linkerd для автоматического retry, circuit breaker и mTLS
Очереди сообщений: Kafka или RabbitMQ для асинхронного взаимодействия между сервисами
Кэширование: Redis для часто запрашиваемых данных
