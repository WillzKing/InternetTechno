Зачем нужен файл .proto? Почему мы не пишем классы сообщений сразу на Python?
Файл .proto это языконейтральный контракт, описывающий структуры данных и сервисов
Он выступает единым источником истины для генерации кода
Мы не пишем классы сразу на Python по двум причинам:
1.1 Кросс-языковая совместимость: сервер на Go и клиент на Python могут работать с одними и теми же структурами, сгенерированными из одного .proto файла, без риска рассинхронизации типов
1.2 Безопасная эволюция схемы: Protobuf принуждает к дисциплине обратной совместимости через нумерацию полей и правила резервирования имен, чего невозможно добиться, просто описывая классы вручную в каждом языке

Что такое Unary RPC? Чем он концептуально похож на REST запрос?
Unary RPC это простейший тип взаимодействия, при котором клиент отправляет один запрос и получает один ответ
Концептуальное сходство с REST:
2.1 Оба предполагают синхронную модель запрос-ответ
2.2 Клиент блокируется (или ожидает Future/Promise) до получения ответа от сервера
2.3 Подходит для операций, где не нужна потоковая передача данных

Почему gRPC обычно эффективнее REST (JSON) по процессору и трафику?
Эффективность достигается за счет трех факторов:
3.1 Бинарный сериализатор: Protobuf кодирует данные в компактный бинарный формат, который весит в разы меньше текстового JSON, так как в нем нет имен полей, кавычек и пробелов
3.2 Строгая схема: парсеру не нужно анализировать структуру на лету и гадать о типах, он заранее знает смещения и типы данных
3.3 HTTP/2: gRPC работает поверх HTTP/2, что дает мультиплексирование (много запросов в одном TCP-соединении), сжатие заголовков (HPACK) и минимизацию оверхеда на установку соединения

Что такое "обратная совместимость" в Protobuf и зачем нужны номера полей (тэги, например = 1)?
Обратная совместимость это возможность сервиса, собранного с новой версией схемы, обмениваться данными с клиентом, использующим старую схему, без ошибок
Номера полей (тэги) это идентификаторы, которые идут в бинарный поток вместо длинных строковых имен
Зачем нужны тэги:
4.1 Они позволяют менять имена полей без потери совместимости, так как десериализатор опирается на номер, а не на имя
4.2 Сервер игнорирует неизвестные ему номера (новые поля, добавленные позже), а для отсутствующих в сообщении номеров подставляет значения по умолчанию, не ломая логику

Что такое Stub (стаб) на клиенте и Servicer на сервере?
Stub (клиентская заглушка) это сгенерированный объект, который выглядит как обычный локальный класс с методами сервиса
Клиент вызывает метод стаба, а стаб внутри себя выполняет сериализацию запроса, отправку по сети и десериализацию ответа, полностью скрывая сетевую логику
Servicer (сервисный интерфейс/базовый класс) это сгенерированный абстрактный интерфейс на стороне сервера
Разработчик наследует Servicer и реализует бизнес-логику в его методах, а gRPC фреймворк берет на себя входящую десериализацию и исходящую сериализацию

В каких случаях вы бы выбрали REST, а в каких — gRPC?
REST выбирают в следующих случаях:
6.1 Публичные API: нужна простая интеграция с любыми клиентами, включая браузеры, где gRPC-клиент сложно использовать напрямую
6.2 Кэширование: HTTP-инфраструктура (CDN, прокси) умеет кэшировать GET запросы по URL
6.3 Простая отладка: JSON читаем глазом и доступен через curl без дополнительных инструментов
gRPC выбирают в следующих случаях:
6.4 Микросервисы с высокой нагрузкой: нужна минимальная задержка и малый объем трафика между внутренними сервисами
6.5 Потоковая передача: необходимы серверные, клиентские или двунаправленные стримы в реальном времени
6.6 Полиглотная среда: строгая кодогенерация для разных языков обеспечивает контракт, исключающий ошибки ручного написания DTO
