Что такое слой в Docker и почему порядок команд в Dockerfile важен для кэширования?
Слой это неизменяемая часть образа, создаваемая каждой инструкцией Dockerfile (RUN, COPY, ADD)
Слои складываются последовательно и образуют итоговый образ, переиспользуясь между разными сборками
Порядок команд важен для кэширования потому что Docker кэширует слои последовательно
Если какой-то слой изменился (или изменились файлы, которые в него копируются), то все последующие слои будут перестроены заново, даже если их инструкции не менялись
Поэтому часто меняющиеся инструкции (COPY кода приложения) помещают в конец, а редко меняющиеся (установка системных зависимостей) в начало

В чем суть Multi-stage build? Какие проблемы он решает?
Multi-stage build это использование нескольких секций FROM в одном Dockerfile, где каждая секция это отдельный этап сборки
Финальный образ собирается путем копирования артефактов из предыдущих этапов с помощью COPY --from
Решаемые проблемы:
2.1 Разделение сборочного и рантайм окружения: компиляторы, SDK и dev-зависимости остаются в промежуточных этапах и не попадают в финальный образ
2.2 Значительное уменьшение размера образа: финальный образ содержит только скомпилированные бинарники или минифицированные статические файлы
2.3 Безопасность: в продакшен не попадают исходный код, ключи сборки, пакетные менеджеры и другие инструменты, которые могут быть использованы для атаки

Зачем нужен файл .dockerignore?
Файл .dockerignore исключает указанные файлы и папки из контекста сборки, который отправляется демону Docker
Это нужно для:
3.1 Уменьшения размера контекста: исключение node_modules, .git, логов и временных файлов ускоряет передачу контекста демону
3.2 Предотвращения инвалидации кэша: если в проекте меняются файлы, не влияющие на сборку (логи, локальные конфиги), они не будут триггерить пересборку слоя COPY
3.3 Безопасности: секреты (.env, ключи) и конфиденциальная информация не попадут в слой образа через COPY

Чем отличаются инструкции CMD и ENTRYPOINT?
CMD задает аргументы по умолчанию, которые передаются команде запуска
Если пользователь передает свои аргументы при docker run, они полностью заменяют CMD
ENTRYPOINT задает основную исполняемую команду контейнера, которая не переопределяется аргументами командной строки
Аргументы docker run в этом случае добавляются как параметры к ENTRYPOINT
Типичная совместная практика:
4.1 ENTRYPOINT: ["nginx"] (фиксированная программа)
4.2 CMD: ["-g", "daemon off;"] (параметры по умолчанию, которые можно переопределить)

Почему рекомендуется использовать COPY вместо ADD?
COPY выполняет простое копирование файлов и директорий из контекста сборки в слой образа
ADD имеет дополнительную скрытую магию, которая делает поведение менее предсказуемым:
5.1 Автораспаковка: ADD автоматически распаковывает tar-архивы и сжатые файлы, что может быть нежелательно и неочевидно
5.2 Загрузка по URL: ADD умеет скачивать файлы из интернета, но не поддерживает удаление после скачивания и не имеет встроенного кэширования, в отличие от RUN curl && rm
5.3 Принцип наименьшего удивления: COPY делает ровно то, что заявлено в названии, не создавая побочных эффектов

Почему приложение в контейнере должно слушать 0.0.0.0, а не 127.0.0.1?
127.0.0.1 это loopback-интерфейс, доступный только внутри самого контейнера
Если приложение слушает 127.0.0.1, то даже Docker-прокси (docker-proxy) и проброс портов (-p) не смогут достучаться до процесса, так как трафик приходит с виртуального сетевого интерфейса, а не с loopback
0.0.0.0 означает все доступные сетевые интерфейсы, включая виртуальный сетевой мост Docker
Это делает порт доступным для других контейнеров в сети Docker и для проброса на хост
