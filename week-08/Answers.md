Что такое Server Streaming? Приведите пример использования.
Server Streaming это тип RPC, при котором клиент отправляет один запрос, а сервер в ответ открывает поток и отправляет множество сообщений с течением времени
Клиент читает этот поток до тех пор, пока сервер не отправит сигнал завершения
Пример использования: сервис мониторинга, где клиент запрашивает логи за определенный период, а сервер стримит найденные записи по мере их появления, вместо того чтобы накапливать огромный массив в памяти и отдавать его разом

Чем Server Streaming отличается от просто получения большого списка (List) в одном ответе?
Отличия заключаются в модели потребления и потреблении памяти:
2.1 Память сервера: при стриминге сервер не обязан загружать все данные в оперативную память для формирования одного гигантского объекта ответа, он отдает элементы по одному
2.2 Время до первого байта (TTFB): клиент получает первый элемент и может начать его обработку или отображение немедленно, не дожидаясь завершения загрузки всего списка
2.3 Ограничения размера: стриминг не упирается в лимиты на максимальный размер одного gRPC-сообщения, так как данные разбиваются на множество маленьких сообщений

Какие метрики производительности существуют (Latency, Throughput, CPU Usage)?
Latency (Задержка) это время, которое требуется одному запросу на полный цикл от отправки клиентом до получения ответа
Обычно измеряется в миллисекундах и смотрится по перцентилям (p50, p95, p99)
Throughput (Пропускная способность) это количество операций, которое система способна обработать за единицу времени
Измеряется в RPS (запросах в секунду) и показывает общую мощность системы под нагрузкой
CPU Usage (Загрузка процессора) это процент времени, которое CPU тратит на вычисления (сериализацию, бизнес-логику), а не на ожидание ввода-вывода
Показывает эффективность кода и наличие узких мест

Почему важно переиспользовать канал (Channel) в gRPC клиенте при замерах производительности?
Переиспользование канала критически важно по трем причинам:
4.1 Установка соединения это дорого: создание нового канала на каждый запрос включает TCP handshake и TLS handshake, что разрушает показатели Latency и грузит CPU лишней криптографией
4.2 Мультиплексирование: единый канал держит одно TCP-соединение и использует HTTP/2 потоки, что позволяет отправлять множество параллельных запросов без оверхеда на новые соединения
4.3 Прогрев соединения: TCP slow start и окна перегрузки набирают скорость только со временем, поэтому при бенчмарках нужно дать каналу прогреться, иначе замеры будут ложнопониженными

В каких сценариях REST может оказаться быстрее или удобнее gRPC?
REST быстрее или удобнее в следующих сценариях:
5.1 Отладка и разработка: JSON-ответ можно прочитать глазами в браузере или через curl без установки дополнительных утилит типа grpcurl
5.2 Кэширование на инфраструктуре: HTTP-прокси (Nginx, Varnish) и CDN понимают семантику GET-запросов (идемпотентность) и могут автоматически кэшировать ответы, снижая нагрузку на бэкенд
5.3 Передача в браузер: для веб-приложений проще использовать REST (JSON + Fetch API), так как полноценная поддержка gRPC-Web требует дополнительного прокси-сервера (Envoy)
5.4 Очень маленькие сообщения с редкими вызовами: в этом случае накладные расходы на бинарную сериализацию Protobuf и поддержание HTTP/2 соединения могут быть неоправданными по сравнению с простым текстовым JSON

Что такое "Head-of-Line Blocking" и как HTTP/2 (и gRPC) решает эту проблему?
Head-of-Line Blocking (блокировка головы очереди) это проблема, когда потеря одного пакета в TCP-соединении приводит к задержке всех последующих запросов в том же соединении
Решение на уровне HTTP/2 (и gRPC):
6.1 HTTP/2 вводит мультиплексирование через стримы (потоки), позволяя отправлять несколько независимых запросов и ответов параллельно в рамках одного TCP-соединения
6.2 Каждый стрим независим, поэтому потеря пакета в одном стриме теоретически не должна тормозить другие
Важное уточнение: HTTP/2 решает проблему на уровне приложения, но физически пакеты все равно идут через одно TCP-соединение, поэтому в случае реальной потери TCP-пакета он все равно заблокирует остальные стримы до переотправки утерянного сегмента (TCP Head-of-Line Blocking)
