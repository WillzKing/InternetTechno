Зачем нужны variables в GraphQL запросе? Почему нельзя просто склеивать строки?
Переменные отделяют структуру запроса от самих данных
Это гарантирует безопасность типов, корректный парсинг спецсимволов и экранирование кавычек на стороне сервера
Склейка строк (интерполяция) уязвима для GraphQL-инъекций, приводит к дублированию кода при повторяющихся аргументах и мешает серверу кэшировать структуру запроса, так как хеш строки меняется при каждом новом значении

Из каких полей состоит стандартный JSON-запрос к GraphQL серверу?
Стандартный JSON-запрос состоит из трех полей:
2.1 query (string, обязательное): строка с телом операции (запроса или мутации)
2.2 variables (object, необязательное): JSON-объект с переменными, переданными в запрос
2.3 operationName (string, необязательное): имя конкретной операции, которую нужно выполнить, если в query их отправлено несколько (нужно для выбора одной)

Почему у GraphQL обычно только один URL endpoint?
GraphQL спроектирован так, чтобы один endpoint мог обрабатывать любые запросы, независимо от типа извлекаемых ресурсов
В отличие от REST, где URL обозначает ресурс, здесь клиент сам описывает форму данных в теле запроса
Единый endpoint упрощает сетевую маршрутизацию, скрывает внутреннюю архитектуру и позволяет клиентам запрашивать данные из разных источников за один HTTP-запрос

Что означает наличие поля errors в ответе сервера? Может ли оно прийти вместе с data?
Поле errors означает, что при выполнении запроса возникли ошибки на уровне GraphQL (например, нарушение типов, провал резолвера или ошибка валидации)
Да, errors может прийти вместе с data
Это ключевая особенность GraphQL: ответ может быть частичным
Сервер возвращает ошибку для проблемной ветки данных в массиве errors, а успешно запрошенные данные все равно приходят в поле data (с null в том месте, где произошел сбой)

Как клиент должен обрабатывать ошибки, если HTTP статус ответа 200?
Клиент не должен ориентироваться на HTTP статус 200 как на признак успеха
Нужно парсить тело ответа и проверять наличие поля errors в корне JSON
5.1 Если errors отсутствует: запрос выполнен полностью успешно
5.2 Если errors присутствует вместе с data: запрос выполнен частично, нужно проанализировать массив errors и обработать частичные данные
5.3 Если errors присутствует без data: запрос не выполнен, ошибка фатальная

В чем плюсы использования типизированных клиентов (например, Apollo Client или Relay) перед простыми HTTP-запросами?
6.1 Нормализованное кэширование: клиенты автоматически склеивают и обновляют сущности в локальном кеше по ключам id и __typename, избавляя от лишних сетевых запросов
6.2 Управление состоянием загрузки и ошибок: предоставляют готовые состояния loading, error и data без написания шаблонного кода
6.3 Колокация (совмещение) данных: фрагменты GraphQL позволяют описывать требуемые данные прямо внутри компонента, который их потребляет
6.4 Генерация типов: на основе схемы и запросов автоматически генерируются TypeScript-типы, исключая рассинхрон между бэкендом и фронтендом
6.5 Оптимистичные обновления UI: позволяют мгновенно отображать результат мутации в интерфейсе до получения ответа от сервера с автоматическим откатом при ошибке
