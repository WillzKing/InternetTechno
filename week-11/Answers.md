Зачем создавать пользовательскую сеть (bridge network) в Docker Compose, если есть дефолтная?
Пользовательская сеть дает контроль и изоляцию, которых нет у дефолтной сети
Причины создания:
1.1 DNS-резолвинг по именам сервисов: в пользовательской сети контейнеры могут обращаться друг к другу по имени сервиса (например, curl http://api), тогда как в дефолтной сети это работает только через устаревшие ссылки (links)
1.2 Изоляция окружений: контейнеры из разных пользовательских сетей не видят друг друга, что позволяет запускать несколько независимых стеков с одинаковыми именами сервисов без конфликтов
1.3 Подключение и отключение на лету: к пользовательской сети можно подключать и отключать контейнеры без их перезапуска, в отличие от дефолтной

В чем разница между build и image в описании сервиса?
build указывает путь к контексту сборки (папка с Dockerfile), заставляя Docker Compose собрать образ локально перед запуском
Используется при разработке, когда образ еще не запушен в регистри
image указывает имя готового образа для скачивания из регистри (Docker Hub, GitLab Registry)
Если указаны оба параметра одновременно, Compose соберет образ из build, но пометит его тегом, указанным в image

Что делает depends_on? Гарантирует ли он, что приложение в зависимом контейнере полностью инициализировалось?
depends_on управляет порядком запуска и остановки контейнеров
При docker compose up он запускает зависимые контейнеры раньше
Нет, depends_on не гарантирует полной готовности приложения
Он ждет только перехода контейнера в состояние started, но не знает, инициализировалась ли база данных или поднялся ли HTTP-сервер внутри
Для гарантии готовности нужно использовать healthcheck в связке с условием depends_on

Как работают healthcheck-и и как использовать их в depends_on?
Healthcheck это инструкция в Dockerfile или Compose, которая периодически проверяет состояние приложения внутри контейнера через заданную команду
Контейнер может иметь статусы starting, healthy или unhealthy
Использование в depends_on:
4.1 В Compose версии 3.8+ (или при использовании docker compose через плагин) можно указать depends_on с условием service_healthy
4.2 Синтаксис: в depends_on добавляется объект с полями service: db, condition: service_healthy
4.3 Тогда Compose не запустит зависимый сервис, пока контейнер с базой данных не вернет статус healthy по результатам healthcheck

Как передать переменные окружения в контейнер через Compose (минимум 2 способа)?
Способ 1: секция environment в описании сервиса
Значения задаются прямо в yaml-файле парой КЛЮЧ=ЗНАЧЕНИЕ
Подходит для несекретных конфигурационных значений
Способ 2: файл .env или указание env_file
Сервис загружает переменные из внешнего файла, указанного через env_file: ./config.env
Сам .env файл не коммитится в репозиторий для безопасности
Способ 3: подстановка shell-переменных
В Compose можно использовать ${VARIABLE} без указания значения, Compose подставит переменную из окружения, в котором запущен docker compose

Почему Docker Compose редко используют в продакшене (хотя это возможно)?
Compose редко используют в продакшене по следующим причинам:
6.1 Однохостовое ограничение: Compose управляет контейнерами только на одном сервере и не умеет распределять нагрузку по кластеру, в отличие от оркестраторов типа Kubernetes
6.2 Отсутствие самовосстановления: если контейнер упал, Compose не перезапустит его автоматически без сторонних инструментов или специальной конфигурации restart-политик
6.3 Нет управления ресурсами: отсутствует встроенный контроль лимитов CPU/памяти между сервисами на уровне планирования
6.4 Нет сложных стратегий деплоя: нет нативной поддержки rolling updates, canary deployments и автоматического отката
